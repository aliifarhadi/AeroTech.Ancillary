## 2. What the catalog offers the engine (source-verified)

- **Profiles and variants.** `AncillaryProfile` 1..9 (Baggage, Seat, Upgrade, Meal, Pet, AssistedTravel, AirportService, Priority, Connectivity); `AncillaryVariant` registry A01..A24 with profile, `ProvisionApplicationType`, allowed `PricingUnit`s and `ServiceDateBasis` values. One typed specification per definition (`Baggage`, `Seat`, `Upgrade`, `Meal`, `Pet`, `AssistedTravel` with five detail records, `AirportService`, `Priority`, `Connectivity`).
- **Selection factory.** `AncillaryServiceDefinition.SelectionContract` (public) returns `CustomerSelectionContract(Kind, ZeroQuantityMeansNoSelection, Fields[Name, Type, Required])` from the internal `CustomerSelectionContract.For`. The engine reads that property; it builds no second registry of forms.
- **Lifecycle selectors.** Definition `ServiceDefinitionStatus` (Draft 1, Active 2, Suspended 3, Retired 4), one Active version per `(OwnerAirlineId, ServiceDefinitionRef)`; Provision `ProvisionStatus` with a unique Active `(ServiceDefinitionId, Sequence)`; Pricing `PricingStatus` with one Active pricing per provision; inventory policy `InventoryRecordStatus` keyed by `(OwnerAirlineId, ServiceDefinitionRef)`.
- **Provision descriptors.** `Sequence`, `CoverageScope` (Sector 1, Portion 2, Journey 3, Order 4), `PurchaseStage` (PreOrder 1, PostTicketed 2, Both 3, LegacyUnspecified 4, OnBoard 5), `PriceOrigin` (Filed 1, ExternalQuote 2, Free 3, NotAvailable 4, LegacyUnspecified 5), `QuoteProviderKey`, `QuantityRule(Unit, Min, Max)`, `Outcome(Disposition Paid 1 / Free 2 / NotAvailable 3, DocumentRequired, BookingRequired)`, `Availability.MustCheckAvailability`, `Fulfillment.FulfillmentProviderKey`, `Settlement`.
- **Ten shared rule groups** (all optional children of the provision): PassengerEligibility, SalesRestrictions, Geography, FlightApplication, FareApplication, TravelDate, DayTimeApplication, AdvancePurchase, BaggageApplication, SeatApplication. **Three profile rules:** PetRule, AssistedTravelRule, AirportServiceRule.
- **Pricing.** `AncillaryPricing(PricingUnit, Version, Status, Rates)`; `AncillaryPricingRate(PassengerTypeCode?, AgeFromInclusive?, AgeToExclusive?, CurrencyId, BaseAmount, Components)` with computed `UnitTotal`, `IncludedTaxes`, `UnappliedFees`, `IsUnitTotalComplete`; `AncillaryPriceComponent(Category Ancillary 1 / Tax 2 / Fee 3, Code, CountryId?, StationAirportId?, Amount, FeeApplicationUnit?, TaxTreatment?)`. `TaxTreatment` AddedToBase 1, IncludedInBase 2, LegacyUnknown 3. `FeeApplicationUnit` OneWay 1, RoundTrip 2, Item 3, SectorOrPortion 4, Ticket 5 and the proportional units 6..10.
- **Inventory.** `AncillaryInventoryPolicy(Authority Unlimited 1 / Local 2 / Supplier 3 / FlightFlow 4, LocalPattern, ProviderKey, CountConsumption, WeightConsumption, SlotConsumption, PassengerUsageLimits, Status)`; typed sources `FlightCountInventory`, `FlightWeightInventory`, `AirportSlotInventory`; read states `InventoryCapacityReadState` NotConfigured 1, Unlimited 2, ConfiguredNotGuaranteed 3, ClosedForSale 4, DelegatedCheckRequired 5, Unknown 6, UnsupportedPattern 7. `PassengerUsageLimit(LimitScope PerOrder 1 / PerFlightOccurrence 2 / PerServiceDate 3 / PerPortion 4, MaxUnits, CountingFamilyCode, ConsumptionUnit, UnitsPerPurchase)` with `KeyFor(PassengerUsageSubject) -> PassengerUsageKey`.

## 4. Provision precedence - P3-OPEN-01 is answered by the approved source

- `docs/AeroTech-Ancillary-v12.1/03-RULE-SEMANTICS-AND-INVARIANTS.md` section 1 (approved Phase 1 freeze): Active provisions are evaluated **`Sequence` ascending; the first provision whose populated rule groups all match is decisive**; its outcome decides Paid, Free or NotAvailable; a matching NotAvailable is an explicit denial and does **not** fall through to a broader Paid provision; no match = not saleable.
- Same section: an empty group or empty collection restricts nothing; OR inside one typed collection, AND across collections and across groups; blackout periods and DayTime `Deny` windows veto; a missing runtime fact for a **populated** dimension is "unsupported context", never allowed.
- Code: one Active provision per `(ServiceDefinitionId, Sequence)` - `ActivateAncillaryProvisionService` / `PublishAncillaryProvisionService` supersede the Active provision at the same sequence, `ReactivateAncillaryProvisionService` refuses with 16306. So two Active provisions of one definition version can never tie on sequence.
- Executable form: `tests/AeroTech.Ancillary.Domain.ConformanceTests/Oracle/ProvisionRuleOracle.cs` (the Phase 1 "test-only reference oracle"). Its `Select` also fixes one more point: an **unsupported-context verdict on an earlier sequence is decisive** - evaluation stops there instead of falling through to a later provision. Section 8 of the document requires Phase 3 to "rerun these exact vectors through the real consumer"; the engine tests will do that.

Consequence: direction is not unknown, no blocking question is registered for it. The engine adds the POS filter first (exactly one published POS per provision, v12.2 chapter 05) and then applies the sequence order inside the definition version.

## 7. Design decisions taken for P3.1 where the pack leaves room (for the Owner's gate review)

1. **Placement.** A new module project next to `ReferenceData`, holding the canonical contract, the engine, its reader ports and their EF implementations, with its own `DependencyInjection`. It references `Domain` and `Persistence`; nothing references it except the host (registration) and the tests. No controller, no MediatR surface.
2. **Catalog projections.** The readers return the existing domain aggregates loaded without tracking (definition with its specification, provision with its rule groups, pricing with rates, policy); the engine never mutates them. No parallel read model is created.
3. **Coverage units.** For each traveller: Sector -> one unit per flight; Portion -> one unit per portion (all its flights, one charge); Journey -> one unit with every flight of the context; Order -> one unit only when the source is a real order. A definition whose provisions use different scopes is evaluated per scope; a unit is matched only against provisions of its own scope, in sequence order.
4. **Decisive insufficient verdict.** As in the oracle, an `Insufficient` verdict on the lowest-sequence candidate ends the evaluation of that unit: the candidate is returned as `InsufficientContext`, a later provision is not tried.
5. **Readiness.** `NotEligible` (no match, only with diagnostics), `Unavailable` (matching NotAvailable, closed for sale, missing or ambiguous filed price), `NeedsVerification` (insufficient context, incomplete price, availability that must be checked but has no usable configuration or reference), `NeedsQuote` (ExternalQuote), `NeedsSelection` (typed form or seat map still to be supplied), `Selectable` (simple opt-in or quantity choice with a complete unit price). A delegated or must-check availability does not hide a candidate; it sets `RequiresCheckAtReserve`.
6. **Non-sellable units** are omitted from an ordinary `Shop`; they are returned only when the filter asks for diagnostics, and never for another point of sale.
7. **Time.** A local date or time is derived only from an instant plus an IANA zone the runtime knows; an offset alone is not accepted as a zone.
8. **Tests.** Engine tests use in-memory readers (domain proof only); the EF readers get SQL tests. Neither is evidence of a connected provider.
