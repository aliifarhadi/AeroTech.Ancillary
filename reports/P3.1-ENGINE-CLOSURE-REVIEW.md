## 4. Engine

`IAncillaryShoppingEngine.ShopAsync(context, filter)` and `EvaluateSelectionAsync(context, candidateIdentity, selection)`; both only read.

1. Validate the context and the filter.
2. Five batched reads, independent of travellers, flights and candidates: Active definitions of the owner, Active provisions of those versions published for exactly the context POS, Active pricings of the filed provisions, inventory configurations (policy + typed sources of the context flights), currency decimals. The engine re-checks status, owner and POS on what the readers return.
3. Per definition, traveller and coverage scope: units (Sector = flight, Portion = portion with all its flights, Journey = all flights, Order only for a real order). Provisions of that scope in `Sequence` order; the first verdict other than "no match" decides - a match, a matching NotAvailable, or an insufficient verdict (as in the Phase 1 oracle).
4. `ProvisionEvaluation`: stage, the ten rule groups, the nine profile checks, the selection contract - three-valued (`Match`, `NoMatch`, `Insufficient`) with reason codes and missing fields.
5. `PriceAssessor`, `QuantityAssessor`, `AvailabilityAssessor` and the readiness, decided in this order (R1): `NotEligible` (no match, or the requested units exceed a verified remaining entitlement); `Unavailable` (NotAvailable provision, no price, closed inventory); `NeedsVerification` (expired source, a missing fact, incomplete price); `NeedsSelection`; `NeedsQuote`; `NeedsVerification` (unverifiable availability, unverified usage or counting family); else `Selectable`. `IsGuaranteed` is always false - `Selectable` is not a stock guarantee.
6. `EvaluateSelection` status (R1) is a function of that readiness: `Selectable` -> `Accepted`; `NotEligible`, `Unavailable` -> `Rejected`; `NeedsSelection`, `NeedsQuote`, `NeedsVerification` -> `Incomplete`.

Ports (in `Reading/`): `IActiveAncillaryDefinitionReader`, `IActiveAncillaryProvisionReader`, `IActiveAncillaryPricingReader`, `IInventoryConfigurationReader`, with EF implementations in `Reading/Sql` (no tracking, split queries). Existing domain ports reused: `ICurrencyReference`, `IInventoryResourceReference`, `IAirportFacilityReference`, `ICountingFamilyReference`, `IFlightFlowDelegationReference`. No usage, seat-map or availability evidence reader was created - no source exists.

None of P3-OPEN-03..06 was touched: no reference, registry or ledger was invented.

Not run in this phase, on purpose: any HTTP smoke, adapter test, token test, hold / confirm / release or concurrency test (P3.2 / P3.3).

Guards that exist in the engine but cannot be reached from an Active catalog, because authoring already refuses the input: a specification service window without a valid IANA zone (domain 16202), an unknown zone id on a specification (16202), fee units 6..10 at pricing publication (16305), a baggage rule whose `ChargeKind` or `AllowanceConcept` contradicts the specification (domain 16321 / rule invariant - `BAG_R1_05` asserts the refusal), a Kilogram usage limit without `UnitsPerPurchase` (policy invariant). They are defensive only and are not counted as proven engine behaviour.

## 10. Decisions and questions for the Owner

### 10.1 R1 questions (each with the fail-closed behaviour that is in the code now)

- **R1-Q1 - pet minimum age.** The Phase 1 selection contract of A13 / A14 has no animal-age field; `AnimalAgeWeeks` exists only on the engine selection type. Today: a declared age below the minimum rejects (`PetTooYoung`), anything else is `NeedsVerification` (`PetAgeNotVerified`), so no pet product with a minimum age can become `Selectable`. Question: is the buyer's declaration enough (then the field must be added to the Phase 1 contract - a Phase 1 change that needs your authority), or must the age come from a document / supplier check (then which source)?
- **R1-Q2 - baggage `TravelApplication`.** No approved text defines AllSectors / AtLeastOneSector / MostSignificantSector / AnySectorOnJourney (v12.1 and v12.2 only list the field). Today: populated = `NeedsVerification`. Question: over which flights (coverage unit or whole journey) and over which criteria does each value quantify? My recommendation, from unverified recollection of the ATPCO optional-services baggage record: AllSectors = every covered flight must satisfy the flight-scoped filters (what the engine already does when the field is empty), AtLeastOneSector = one covered flight is enough; the other two need a most-significant-sector fact and journey facts the context does not carry and should stay blocked.
- **R1-Q3 - baggage `RuleDeference`.** No approved meaning for MarketingCarrier / OperatingCarrier. Today: populated = `NeedsVerification`. Question: what must the engine compare (owner airline against the marketing or operating airline of which flight)?
- **R1-Q4 - `PurchaseApplication`.** Read from the member names only: Prepaid and PrepaidAndCheckIn are offered by shopping; CheckIn does not match in the PreOrder / PostTicketed / OnBoard stages, so a later sequence may match. Keep it?
- **R1-Q5 - allowance concept.** The effective `AllowanceConcept` (rule, else specification) is matched against the verified allowance facts of each covered flight: pieces known = Piece concept, only a weight known = Weight concept. Consequence: a weight package (A02) is offered only on a weight-concept allowance, an extra piece (A01) only on a piece-concept allowance. Is this derivation right, or should the context carry an explicit concept fact?
- **R1-Q6 - rule `Weight` / `WeightUnit`.** Read as a duplicate of the specification weight (`PackageWeightKg` for a weight package, else `MaxKgPerPiece`): equal kilograms pass, any other value or pounds is `NeedsVerification`. Confirm, or name the other meaning.
- **R1-Q7 - `ChargeCombination`.** Separate / empty = no restriction; Combined and MutuallyExclusive are `NeedsVerification` because the context has no "other charge on the same bag" fact. Which fact should decide them?
- **R1-Q8 - expired source.** `ValidUntilUtc <= EvaluatedAtUtc` keeps the candidates but makes them `NeedsVerification` with `SourceContextExpired` (a typed, non-actionable result). Do you prefer a refused request instead?
- **R1-Q9 - order-level fee.** With an unapplied ticket / one-way / round-trip / sector fee the unit price is complete, `RequestedQuantityTotal` is null and `IsOrderLevelTotalComplete` is false; the candidate stays `Selectable` and a valid selection `Accepted`. Is that acceptable, or must such a candidate wait for the order-level total?
- **R1-Q10 - seat facts.** `AncillaryShoppingContext.SeatCharacteristicFacts` is a new context member (flight, seat number, codes, evidence, authority). Approve the shape. A seat number on a provision that restricts seat numbers only (no characteristic on the rule or the specification) is still accepted without a seat-map fact - should that also wait for evidence?
- **R1-Q11 - members the engine does not read.** Section 11 lists every authored member the engine ignores. Which of them are restrictions that must fail closed (my candidates: the terminal of an airport service, `RequiresAdjacentSeat`, `MaxInfantWeightKg`)? Nothing was changed for them in R1.

### 10.2 Still open from the first closure

- **Q1 - definition sales dates.** Zone and inclusiveness of `SalesEffectiveFrom` / `SalesDiscontinueOn`; today decided only when the day is the same in every time zone.
- **Q2 - 29 February birthdays.** Age follows the frozen oracle formula.
- **Q4 - exit-row eligibility.** A traveller with unknown `VerifiedExitRowEligible` is `NeedsVerification` already at `Shop`.
- **Q5 - unverifiable availability.** Such a candidate is returned as `NeedsVerification`, not hidden.

(Q3 of the first closure is now R1-Q1.)

### 10.3 Decisions of the first closure that stay as they were

1. Coverage units per scope; a unit is matched only against provisions of its own scope.
2. An insufficient verdict on the lowest-sequence provision ends the evaluation of that unit (same as the Phase 1 oracle). The same order applies inside one provision: an unknown fact outranks a mismatch, so a selection that is wrong and also unverifiable is `Incomplete` with its field issue listed, not `Rejected`.
3. On a multi-flight unit every covered flight must satisfy every populated flight-scoped filter, date, time and lead-time rule.
4. Geography on a Portion / Journey unit is evaluated per portion; coverage country = destination country.
5. Cabin and RBD of a fare filter fall back to the flight's values when the fare fact has none.
6. The excess-piece tier counts the traveller's Active existing services with the same `ServiceDefinitionRef` on the unit's flights.
7. Eligibility is `InsufficientContext` when a fact or a rule-bound selection is missing, `Eligible` when only the typed form is still to be filled.
8. `EvaluateSelection` re-runs the sequence order with the selection and may land on another provision of the same definition.
9. `ChildRef` of the unaccompanied-minor contract is implied by the candidate's traveller.
10. Non-sellable units appear only when the filter asks for them; another point of sale never sees anything.
