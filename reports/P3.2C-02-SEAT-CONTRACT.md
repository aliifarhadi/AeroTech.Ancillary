## 2. The fields of each variant

What the read returns and what the form has to send. A member not listed for a variant is not part of that variant's contract.

| `specification` member | A07 Standard seat | A08 Preferred seat | A09 Extra seat |
|---|---|---|---|
| `seatCharacteristicCodes` | optional list | **at least one** | optional list |
| `applicableCabinIds` | optional list | optional list | optional list |
| `requiresExitRowEligibility` | yes | yes | yes |
| `requiresAdjacentSeat` | - | - | yes |
| `extraSeatPurpose` | - | - | **required** (`PassengerComfort`, `CabinBaggage`) |
| `extraOccupiedSeatCount` | - | - | **required, >= 1** |
| `requiresExternalTicketAction` | - | - | yes |

Compatibility spelling (v1): `seatPurpose`, `requiresAdjacentSeat`, `extraSeatPurpose`, `extraOccupiedSeatCount`, `requiresExternalTicketAction` may still be sent on every variant. They must agree with the variant (`seatPurpose` = the variant's purpose, the two flags `false`, the two extra-seat members `null` on A07 / A08); anything else is refused by the unchanged domain rule with `422` / `16202`.

Where the rule lives: the invariant stays in `Domain/.../Specifications/SeatSpecification.cs` (not edited). The presentation knows two things only: which members each variant shows (`Query/.../Dto/SeatVariantSpecificationDtos.cs` + `SeatVariantSpecificationMapper`) and which purpose a variant implies when the body omits it (`RestApi/.../Requests/SeatSpecificationRequest.cs`). Both are held against the domain by the round-trip tests of section 5.

Seat definition versus seat selling: the definition carries no price, no point of sale and no seat list. A body member such as `price`, `pointOfSaleId` or `availableSeats` is refused at binding (`P32C_SEAT_05`).

## 7. Differences from the proposal of the step-1 report, and open points

1. `ownerAirlineId` and `serviceDefinitionRef` are in the header of the edit view, not inside `form`. Reason: the `PUT` body refuses unknown members, and these two cannot be changed; with them outside, `form` is literally the `PUT` body.
2. Field rules as data on `GET .../Variants` (row 3 of the step-1 matrix) were **not** built. Under the Owner's answer D1 the variant's own schema carries the rule, and no consumer that needs it at run time was found. It can be added if the Backoffice form is to be generated at run time.
3. `RestApi` now reads three constants of the domain catalog (`AncillaryVariant.StandardSeat` ...) to name the variants. It is the first `using` of the Domain project in `RestApi`; the alternative is to repeat the codes as text.
4. Error responses (`400`, `401`, `403`, `404`, `409`, `422`) are not yet declared in OpenAPI. A malformed or unknown-member body is answered by ASP.NET's own `400` problem document, while a validation failure is answered in the service's `{ "errors": [...] }` envelope; this difference exists on every route and belongs to step 5 (error contracts).
5. The request examples are not embedded in the OpenAPI document; they are the three fixture files.
6. Schema names of generic types are still the generator's default (for example `SeatSpecificationRequestDefineServiceDefinitionRequest`); renaming belongs to step 5.
7. Step 3 repeats this for the other eight profiles (21 variants) with the same service, mapper pattern and test shape.
