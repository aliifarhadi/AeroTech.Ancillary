### 4.1 Definitions: one typed write path per profile

| Method | Path | Body | Answer |
|---|---|---|---|
| POST | `/v1/AncillaryServiceDefinitions/{Profile}` | `DefineServiceDefinitionRequest<Spec>` | `ApiResult` with the new id |
| PUT | `/v1/AncillaryServiceDefinitions/{Profile}/{serviceDefinitionId}` | `ChangeServiceDefinitionRequest<Spec>` | `ApiResult` |
| GET | `/v1/AncillaryServiceDefinitions/{Profile}/{serviceDefinitionId}` | — | `BackofficeServiceDefinitionFormDto<VariantSpec>` |

`{Profile}` is one of `Baggage`, `Seat`, `Upgrade`, `Meal`, `Pet`, `AssistedTravel`, `AirportService`, `Priority`, `Connectivity`. These are exactly `ANCILLARY_PROFILES`; do not re-case them. The slug `airport-services` maps to the path segment `AirportService`.

These routes already exist and are unchanged:

- `GET /v1/AncillaryServiceDefinitions/Paginated`;
- `GET /v1/AncillaryServiceDefinitions/Variants?Profile=`;
- `GET /v1/AncillaryServiceDefinitions/{id}`;
- `POST /v1/AncillaryServiceDefinitions/{id}/{Activate|Suspend|Reactivate|Retire|Revise}`.

**Define body (camelCase JSON):**

```text
ownerAirlineId: int          (create only)
supplierId: long
serviceDefinitionRef: string (create only, ^[A-Z0-9_]{1,30}$)
serviceSubCode: string       (^[A-Z0-9]{3}$)
subCodeSource: Industry | CarrierDefined
serviceTypeCode: string|null groupCode: string|null subGroupCode: string|null
description1Code: string|null description2Code: string|null
pricingUnit: PricingUnit     (must be one of the variant's pricingUnits)
serviceDateBasis: ServiceDateBasis (must be one of the variant's serviceDateBases)
variantCode: string          (a variant of this profile)
documentRouting: NoAncillaryDocument | Emd | TicketOrExchange
specification: <the variant's specification, table 4.1.1>
commercialName: string (1..100)   description: string|null (1..500)
document: { type: None|EmdAssociated|EmdStandalone, rfic: string|null, rfisc: string|null }
booking:  { method: Ssr|AuxiliarySegment|DisplayPriceContactCarrierForBooking|NoBookingProcessRequired|PerServiceRecord,
            ssrCode: string|null, ssimCode: string|null, confirmationRequirement: Immediate|SubjectToConfirmation|null }
salesEffectiveFrom: yyyy-MM-dd|null   salesDiscontinueOn: yyyy-MM-dd|null
```

The Change body is the same without `ownerAirlineId` and `serviceDefinitionRef`. The header rules and the document and booking rules are already encoded in `seat-definition-schemas.ts`; promote them, do not rewrite them.

**GET answer:**

```text
{ id, ownerAirlineId, serviceDefinitionRef, version, status{value,name,title}, profile{...}, variantName,
  supplierName, createdAt, activatedAt, suspendedAt, retiredAt,
  form: { supplierId, serviceSubCode, subCodeSource, serviceTypeCode, groupCode, subGroupCode,
          description1Code, description2Code, pricingUnit, serviceDateBasis, variantCode, documentRouting,
          specification, commercialName, description,
          document{type,rfic,rfisc}, booking{method,ssrCode,ssimCode,confirmationRequirement},
          salesEffectiveFrom, salesDiscontinueOn } }
```

`form.specification` has **exactly the members of the variant named by `form.variantCode`** (table 4.1.1). Sending that specification back unchanged is a valid PUT. The request types also accept older discriminator members (`chargeKind`, `mealKind`, `transportMode`, `assistanceKind`, `kind`, `bassinet.requiresInfantAndGuardian`, `unaccompaniedMinor.guardianContactRequired`). **Do not send them.** The server derives them from `variantCode`; if you do send them they must agree, otherwise the answer is 422 with code 16202.

**Create form** (`GET …/ProvisionForm`):

```text
{ serviceDefinitionId, variantCode, profile{value,name,title}, definitionStatus{...}, pricingUnit{...},
  serviceDateBasis{...}, applicationType{...}, allowedRuleSections: string[],
  constraints: { quantityUnit{...}, maxQuantity: int|null,
                 allowedDispositions: EnumValue[], allowedPriceOrigins: EnumValue[], allowedPurchaseStages: EnumValue[] } }
```

**Edit form** (`GET …/Provisions/{id}/Form`):

```text
{ id, serviceDefinitionId, status{...}, profile{...}, variantCode, editable: bool, allowedRuleSections, constraints,
  createdAt, activatedAt, suspendedAt, retiredAt, form: <exactly the members of the profile's PUT body> }
```

`allowedRuleSections` holds PascalCase keys from `PassengerEligibility`, `SalesRestrictions`, `Geography`, `TravelDate`, `DayTimeApplication`, `AdvancePurchase`, `FlightApplication`, `FareApplication`, `BaggageApplication`, `PetRule`, `AssistedTravelRule` and `AirportServiceRule`:

- `FlightApplication` and `FareApplication` are present only when the definition's `serviceDateBasis` is `FlightDeparture`. AirportService products dated by `ServiceStart` do not get them; the server refuses them with 16313. Render exactly the allowed sections and nothing else.
- Each profile section appears only for its own profile.

How the constraints drive the form. The server enforces every one of these at Define/Change; the form must not offer what will be refused:

- **Disposition** select = `allowedDispositions`. A11 (free special meal) and A15 (wheelchair) give `[Free, NotAvailable]`; everything else gives `[Paid, Free, NotAvailable]`.
- **Price origin** select = `priceOriginsFor(disposition) ∩ allowedPriceOrigins`. A Paid Upgrade gives Filed only for `FixedAncillary`; the other Upgrade kinds give ExternalQuote only, which needs `quoteProviderKey`.
- **Purchase stage** select = `allowedPurchaseStages`. A Connectivity product whose `deliveryStage` is OnBoard gives `[OnBoard]`; everything else gives `[PreOrder, PostTicketed, Both]`.
- **Quantity**: the unit comes from `quantityUnit`. `maxQuantity` caps the maximum (1 for A07/A08; null otherwise).
- **Create defaults** come from the constraints, never from a literal. Take the first allowed disposition, the first matching price origin, `Both` when it is allowed (otherwise the first allowed stage), and the `quantityUnit`. Seat's `emptySeatProvisionForm` hard-codes `Paid`/`Filed`/`Both`, which is wrong for A11, A15 and OnBoard Connectivity.

Seat keeps its own `SeatProvisionConstraintsDto`. It has `quantityUnit`, `maxQuantity`, `requiresSeatNumberOrCharacteristic`, `seatNumberFilterRequiresAircraft` and `requiresPreferredCharacteristic`, and no allowed lists. In the shared model, treat absent allowed lists as "every value", which is today's Seat behaviour.

| `baggageApplication` | `freePieces?` int, `firstExcessPiece?` int, `lastExcessPiece?` int, `weight?` decimal, `weightUnit` (Kg), `travelApplication?` (AllSectors\|AtLeastOneSector\|MostSignificantSector\|AnySectorOnJourney), `purchaseApplication` (Prepaid\|CheckIn\|PrepaidAndCheckIn), `ruleDeference?` (MarketingCarrier\|OperatingCarrier), `chargeKind?` (ExtraPiece\|WeightPackage\|Overweight\|Oversize\|SpecialEquipment), `allowanceConcept?` (Piece\|Weight) | `freePieces ≥0`; `firstExcessPiece ≥1`; `lastExcessPiece ≥1`; `first ≤ last`; `weight > 0`, `< 10,000,000`, 2 decimals; `chargeKind = WeightPackage` ⇒ `allowanceConcept = Weight` and a weight; `chargeKind = ExtraPiece` ⇒ `allowanceConcept = Piece`. A frontend that does not load the definition cannot pre-check the publish-time rules. Show them as `RuleAccordionNote` text, and let publish errors surface through the existing publish flow.

#### 4.2.2 Cancellation rules (`settlement.cancellationRules`, all nine profiles, Seat included)

```text
CancellationRule {
  ruleRef: string                       required, trimmed, 1..50, unique within the provision
  reasonKind: Voluntary | Involuntary | SupplierFailure | NoShow
  beforeStartMinutesFrom: int|null      >= 0, inclusive lower bound; null = 0
  beforeStartMinutesTo: int|null        > 0, exclusive upper bound; null = open; when both set, from < to
  penaltyKind: None | FixedAmount | Percentage | ProviderQuoted | ManualReview
  penaltyFixedAmount: decimal|null      only FixedAmount: >= 0, scale <= the currency's decimals; else null
  penaltyCurrencyId: int|null           only FixedAmount: a currency id (`currencies` options); else null
  penaltyPercentage: decimal|null       only Percentage: > 0 and <= 100, at most 4 decimals; else null
  percentageBase: ServiceBase | ServiceTotal | null   only Percentage (required); else null
  waiverPermitted: bool                 a waiver may be considered with evidence; it does not waive by itself
  sourceReference: string|null          1..256, not blank; REQUIRED unless penaltyKind is ProviderQuoted or ManualReview
}
```

List rules:

- no null item;
- no duplicate `ruleRef` (ordinal comparison);
- rules of the **same** `reasonKind` must not overlap on the half-open window `[from ?? 0, to ?? ∞)`.

Breaking any of these answers 422 16302 with the field `ProvisionCancellationRule.<Member>`, or `CancellationRules` for a null item. A currency whose decimals the amount exceeds answers on `ProvisionCancellationRule.PenaltyCurrencyId`. The frontend cannot know currency decimals, so only enforce the money pattern.

Semantics:

| Operation | `cancellationRules` | Effect |
|---|---|---|
| POST | omitted, null or `[]` | no rules |
| POST | list | these rules |
| PUT | omitted or null | stored rules kept |
| PUT | `[]` | stored rules cleared |
| PUT | list | stored rules replaced; an unchanged row is reused |
| GET form | — | the member is **omitted** when there are no rules, so `settlement` keeps its four original members; when there are rules it is a list |

Frontend decision, to be confirmed in the pre-flight report:

- The form always holds `cancellationRules: CancellationRule[]`, seeded from `form.settlement.cancellationRules ?? []`.
- The body builder **always sends the array**, on POST and on PUT.
- The GET form returns every stored rule, so sending the edited array is exact, and `[]` is an explicit clear.
- Without rules, a provision still publishes. Missing rules do **not** mean free cancellation: Stage 3 quotes them through the provider or a manual review. Put that sentence in the editor's `RuleAccordionNote`.

Money and decimals. Send `penaltyFixedAmount` as a decimal string matching `AMOUNT_PATTERN`, exactly like the pricing money. Send every other decimal as a JSON number parsed from validated text (`penaltyPercentage`, kg, cm). Read-back decimals arrive as JSON numbers; convert them to text in the form model.

UI rules:

- Show only the members of the chosen `penaltyKind`. Switching kind clears the other kind's members in the reducer.
- Enter windows in minutes and echo them in days and hours. Keep the conversion in a pure `domain/` function.
- Prefill a unique `ruleRef` suggestion that the user can edit.
- Read-only provisions (`editable: false`) show the rules without controls.

### 4.3 Errors (branch on `kind` and `code`, never on message text)

| Code | HTTP | Where | Meaning | UI |
|---|---|---|---|---|
| — | 400 | any typed body | FluentValidation; `fieldErrors` keyed like `Settlement.CancellationRules[0].RuleRef`, `BaggageApplication.Weight` | map to fields through a pure path → field-name function; the rest go to the banner |
| — | 400 | any typed body | an unmapped member (strict request) | it is a body-builder bug; the banner shows the title |
| 16219 | 409 | provision routes | the definition belongs to another profile | `ErrorState` in the modal |
| 16301 | 404 | provision routes | the provision belongs to another product type | `ErrorState` |
| 16321 | 409 | GET form, Define/Change, publish | the stored provision carries another profile's section, or a value the variant does not allow or that widens its specification | banner, or `ErrorState` on the GET |
| 16323 | 409 | Define/Change | purchase stage not allowed for the variant | prevent it with the constraints |
| 16313 | 409 | Define/Change | a flight-bound section on a product dated by ServiceStart | prevent it with `allowedRuleSections` |
| 16302 | 422 | Define/Change | "Provision field X is invalid." | banner (the title names the field) |
| 16320 | 422 | Define/Change | outcome and price origin mismatch | prevent it with the selects |
| 16303 | 409 | Change | not a draft | read-only view |
| 16202 | 422 | definitions | "Service definition field X is invalid." (e.g. `PetSpecification.AllowedHoldAnimalSizeBrackets`) | banner |

| 16204, 16205, 16206, 16207, 16208 | 409/422 | definitions | ref already active, supplier missing or inactive, industry sub code missing or conflicting | banner |

## 5. Target architecture

Boundaries:

- Server Components load list pages, as they do today.
- Editors are client islands (`Modal` + React Query), exactly like Seat.
- Option data comes from `useAncillaryOptions` inside the modals.

### 5.1 Layering per layer

| Layer | Rule |
|---|---|

## 7. UI states (every editor)

- **Loading**: `TableSkeleton` inside the `Modal`, as Seat does.
- **Load error**: `ErrorState` with `GatewayError.title`.
- **Read-only** (`editable: false`, or a definition that is not a draft): values only, the footer shows Close.
- **Pending mutation**: the submit `Button` shows `loading`/`loadingLabel`; Cancel is disabled.
- **Validation**:
  - validate on submit with `useFieldValidation`;
  - the first failure feeds the banner and every failed field is marked;
  - the first invalid control is focused;
  - backend `fieldErrors` mark their fields;
  - business codes go to the `FormAlert`.
- **Unknown sections**: the server allows a section the screen does not know. Keep Seat's warning `FormAlert`.
- **Lookups**: when lookups fail, keep Seat's warning listing the failed kinds.
- **Success**: close and refresh exactly as Seat does (`router.refresh()` for definitions, query invalidation for provisions). Show no success message that unmounts at once.
- **Responsive**: keep the `rule-modal-*` layout of the Seat modals on desktop, tablet and mobile.
- **Theme**: light and dark through tokens only.

## 8. Accessibility and security

- Use only `Field`, `Input`, `Textarea`, `NativeSelect`, `Checkbox` and `Radio`, plus the existing composites (`MultiSelectField`, `TokenListField`, `AirportAutocomplete`, `RuleAccordion`, `Table`).
- Every control has a label. Remove buttons name their rule ("Remove rule VOLUNTARY_LATE").
- The rule list is announced as a list, and focus moves to the new rule card on Add.
- Every body is validated server-side in the BFF with its family's strict schema.
- No token reaches the client. No raw backend message is shown: `sanitizeUserFacingText` already runs.

## 12. Prohibited shortcuts

- No `react-hook-form`, no new state library, no new dependency, no raw `<select>`/`<input>` and no Radix import from a feature.
- No `fetch("/api/…")` from a component, and no envelope parsing in a component.
- No payload builder, normaliser or business rule in a `.tsx` file.
- No `as SomeType` on a request body in a BFF handler. Each BFF route validates with its family's schema.
- No second implementation of a section, schema piece or service that already exists for Seat. Promote it.
- No invented field, route, enum value or error code. Everything here is quoted from the backend source; if the running backend disagrees, stop and report.
- No literal palette colour, hex or numeric z-index.
- No change to search-param names or URLs.
