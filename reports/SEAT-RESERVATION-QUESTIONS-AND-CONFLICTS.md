## 1. How the sibling does it (FlightFlow `k8s-stg@962f418`, read in source)

| Topic | FlightFlow (`AeroTech.FlightFlow.RestApi/V1/FlightAggregate/Controllers/ServiceController.cs`, Domain `Flight.cs`, `FlightGuards.cs`, `FlightSeatHold.cs`) |
|---|---|
| Hold | `POST Service/v1/Flights/Seat-Holds` → 201 `{ holdId, idempotencyKey, reference, expiresAt, seats[{ flightId, paxReference, seat, seatHoldStatus, seatHoldReference }] }`. `HoldId` is generated by the service (`idGenerator.GetNewId()`), `IdempotencyKey` and `Reference` come from the caller, `ExpiresAt` is required. Same key → the existing hold is answered (`TryGetExistingHold`). One distributed lock per flight, one commit. |
| Confirm | `POST Seat-Holds/{id}/Confirmations` → 204. Guard: all Held or all Confirmed = ok (replay is a no-op); Expired / Released / Cancelled / mixed → own error each (1176–1179). |
| Release (before confirm) | `DELETE Seat-Holds/{id}` → 204. Guard: Held or already Released = ok; Confirmed / Expired / Cancelled / mixed → errors 1182–1185. |
| Cancel (after confirm) | `POST Seat-Confirmations/{id}/Cancellation { seatHoldReferences[], reasonCode }` → Confirmed → Cancelled with a reason (partial by unit refs). Guard: Confirmed or already Cancelled = ok; Held / Released / Expired → 1187–1189. |
| Extend | `PATCH Seat-Holds/{id} { expiresAt }`. |
| Expire | Status is lazy (`StatusAt(now)`) AND persisted by the Quartz job `ReleaseTimeoutReservedJob` (cron `Jobs:ReleaseTimeoutReserved`) → `ExpireHeldFlightSeatsCommand` → `flight.ExpireSeatHolds` (Held with ExpiresAt ≤ now → Expired, one commit per run). |
| Statuses | `FlightSeatHoldStatus` Held=1, Released, Expired, Confirmed, Cancelled. |
| Consumer | Ordering.Final `Providers/FlightFlow/Services/FlightFlowReservationProvider.cs` implements `Domain/Providers/Reservation/IReservationProvider` (Reserve / Read / Release / Confirm / CancelConfirmed) and maps the FlightFlow error codes 1176–1189; `ReserveService` groups the order's services by `FulfillmentProviderKey` and calls one provider per group. An Ancillary provider does not exist in Ordering yet (Ordering is on hold). |

## 3. Open points (answer inline)

**Q1. Seat hold route and input.** Your directive proposes `POST Service/v1/Ancillaries/SeatMaps/Holds { orderId, idempotencyKey, reference, requestedExpiresAt, seats: [{ orderServiceId, seatMapSelectionId }] }` as a typed facade over the existing `HoldAncillaryServicesService` (CLAUDE rule 2). The facade decodes each id, reads its pricing → provision → definition (the Resolve lookup), builds one unit per seat (`quantity 1`, `CoverageScope Sector`, `CoveredFlightIds [flightId]`, traveller = ?) and calls the one existing hold path. Confirm / Release / Cancel / GET stay on `Service-Holds/{holdId}` for every ancillary.
- Recommendation: yes, exactly that.
- Answer: `POST Service/v1/Ancillaries/SeatMaps/Holds { orderId, idempotencyKey, reference, requestedExpiresAt, seats: [{ orderServiceId, travellerId, XXX }] }` XXX=every other parameter that is needed for validation of selected seat like flightnumber or passengertype or departuredate

**Q2. Traveller on the unit.** The unit needs `TravellerId` (> 0 for Sector). The seat id carries `travellerRef` (text), not the Ordering traveller id.
- (a) the seat input carries `orderTravellerId` beside `orderServiceId` (Ordering knows both); (b) store the ref text instead of the id.
- Recommendation: (a); Ordering is the only caller and has both ids.
- Answer: based on Q1

**Q3. Seat facts on the unit.** To make replay / conflict checks exact ("same key, another seat → conflict"), the unit stores `SeatMapSelectionId` (nullable, max 256) and `SeatNumber` (nullable, max 16, upper). Plain migration on both contexts; dev data wiped per your standing rule.
- Recommendation: yes; also `PricingId` so Ordering can read back which pricing was held.
- Answer:yes; also `PricingId` so Ordering can read back which pricing was held.

**Q4. Release and Cancel routes.** Sibling shape: `DELETE Service/v1/Ancillaries/Service-Holds/{holdId}` (Held → Released, idempotent; Confirmed / Expired / Cancelled refused) and `POST Service-Holds/{holdId}/Cancellations { reasonCode }` (Confirmed → Cancelled, all units, idempotent; Held / Released / Expired refused). No partial cancel by unit in this round.
- Recommendation: both now, whole hold only.
- Answer: both now, whole hold only.

**Q5. Persisted expiry.** Ancillary has no Quartz; its background work is `BackgroundService` pollers in `Consumers/Jobs` (`MessageRetentionPoller`). Proposed: `AncillaryHoldExpiryPoller` with `Holds:ExpiryPollIntervalSeconds` (fail-fast when missing), marking Held holds with `ExpiresAt ≤ now` as Expired (hold + units) through the aggregate, one save per hold. `RequestedExpiresAt` becomes required on the seat facade (the generic route keeps it optional).
- Recommendation: yes.
- Answer: yes

**Q6. Concurrency.** Two concurrent holds with different keys for the same `OrderServiceId` can both pass the query check today. Sibling: lock. Proposed: `IDistributedLock.AcquireAsync($"ancillary-hold:{orderId}", …)` around the hold path (Ordering locks per order too: `IReservationLock.AcquireAsync(orderId)`); lock expiry from `Holds:LockTimeout`.
- Recommendation: yes, per order id, inside the existing service.
- Answer: yes, per order id, inside the existing service.
