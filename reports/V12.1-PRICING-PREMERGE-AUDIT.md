## 0. What the Owner should know first

1. **The current model is arithmetically coherent for one currency per Pricing, and that is proven by execution**: EUR base 50 + tax 5 + fee 2 gives one rate with total 57 (section 3).
2. **"Currency on the parent, amounts on the children" is not in itself the defect.** The official Amadeus `Price` schema has exactly that shape: one `currency` on the price object, `fees[]` and `taxes[]` with an amount only (section 6). The real defects are elsewhere: no currency validation of any kind, a fixed two-decimal rule, no way to author two currencies, no tax-inclusion statement, and line identities that are regenerated on every draft edit.
3. **`ReferenceData.Currencies.DecimalPlaces` cannot be used as it stands.** On the dev database 168 of 170 currencies have `DecimalPlaces = 0`, including KWD, BHD and OMR (three minor digits in ISO 4217) and GBP, CHF, AED (two). Only EUR and USD carry 2. Validating amounts against this column today would reject GBP 10.50 and KWD 10.125. This directly affects decision D07 and scenarios P09–P15 of the completion pack (section 10).
4. **`FeeApplicationUnit` describes the service charge itself, not a "Fee" component.** The official ATPCO help text says so, the enum mirrors the ten ATPCO values, and on dev all 69 pricings carry a unit while not one Fee line exists. Moving the unit onto Fee components only (proposal D06) would leave every existing price without it (sections 5 and 10).
5. **Nothing in this repository consumes a Pricing.** No quote, no selected rate, no traveller / segment / quantity / tax snapshot exists. Every question about source, sale or billing currency at quote time is `UNIMPLEMENTED` here.

## 5. Version switch, restrictions, and where they diverge from an airline offer contract

Switch (`SwitchActiveAncillaryPricingService.cs:39–79`): load provision and target pricing; provision must be priceable; units must match; a stale `ExpectedOldPricingId` → 16510; the current Active is superseded (Retired) and projected; the target is activated (or reactivated from Suspended); one `SaveChanges`. The read model is written by the same unit of work but in a second context, not in the same database transaction (inherited behaviour, listed in the Phase 2 report).

Confirmed present restrictions:

| Restriction | Where enforced |
|---|---|
| one Active Pricing per Provision | service check + filtered unique index |
| one currency per Pricing | structural: single `CurrencyId` on the root |
| `FeeApplicationUnit` on the root, not on a line | structural |
| passenger type / age selectors only for `PerPassenger` | `AncillaryPricing.cs:228–231` |

Where this is inconsistent with what an airline NDC / PSS offer has to state:

| Topic | Current | Issue |
|---|---|---|
| Money | amount without currency on the line, currency once on the root | coherent, but nothing validates the currency or its minor units, so an amount can be filed that the currency cannot represent |
| Several selling currencies / markets | one currency; a second market needs a second provision | ATPCO files the amount with a currency or a **currency table** per provision (verified, section 6). Duplicating the provision works but repeats all eligibility rules and must be kept in step by hand |
| Tax inclusion | none | ATPCO has one "Tax Included" check box per provision (verified). Without it a consumer cannot tell 55-inclusive from 55-plus-tax |
| Fee application unit | root, 5 of 10 values activatable | the unit is ATPCO's "applies per" of the **service charge**; it belongs with the base amount. It is not a property of a separate Fee component (see section 10, D06) |
| Rate identity | none; a rate is a group of sibling lines | an offer item must reference the price it was built from; there is no stable id to reference, and line ids change on every draft edit |
| Explainability | no record of which rate was chosen for whom | `UNIMPLEMENTED`; needed before any quote exists |

## 6. Benchmark comparison

Authoring / publishing (what an airline files) and the shopper quote (what a buyer is offered) are different contracts. A database does not have to mirror an API's JSON.

| Source | Status in this audit | What it shows |
|---|---|---|
| ATPCO FareManager help, Optional Services, "View Provisions Details" | **verified** (page retrieved 2026-10-09) | "Fee Application (applies per)": ONE WAY, ROUND TRIP, ITEM, SECTOR/PORTION, TICKET, PER 1KG OVER, PER 5KG OVER, .5 / 1.0 / 1.5 PCT OF FARE PER KG — "whether the optional service charge applies per one of those specified units". "Amount/Currency/Currency Table": amount and currency of the service fee, or a currency table. "Tax Included": whether fee amounts are inclusive of applicable taxes. "Must Check Availability": availability must be checked for pricing. This is an **authoring** benchmark. |
| Amadeus Flight Offers Search v2 OpenAPI (`amadeus4dev/amadeus-open-api-specification`) | **verified** (specification retrieved) | `Price`: `currency`, `total`, `base`, `fees[]`, `taxes[]`; `Fee` = `amount`, `type`; `Tax` = `amount`, `code` — **no currency on a fee or a tax**. `Extended_Price` adds `grandTotal`, `billingCurrency`, `additionalServices[] {amount, type}`. `TravelerPricing` binds a `price` to `travelerId` and `fareDetailsBySegment`. This is a **quote** benchmark. |
| Sabre Stateless Seats API 1.4 | **UNVERIFIED** — the reference page is rendered by script and returned no schema; an older documentation URL returned 404 | nothing is claimed about its fields here |
| Iberia NDC OfferPrice 24.1 | **UNVERIFIED** — the page returned HTTP 403 | nothing is claimed about its fields here |

Reading against the current source:

- Filing one currency per price object with currency-less tax and fee amounts is what the verified quote contract does. The current topology is therefore defensible; an explicit `Money` on every row is a stricter local choice, not something these sources require.
- What both verified sources have and the current model lacks: a statement of tax inclusion, a way to give more than one currency for the same provision, and — on the quote side — the binding of a price to a traveller and segments with a billing currency. The first two are authoring gaps in this repository; the third belongs to a consumer that does not exist yet.

## 9. Recommendation (not approved for implementation)

**Recommended: the three-level model (Pricing → Rate → Component)**, on one condition and with three corrections to the proposal as written.

Condition: it pays for itself only if the Owner wants more than one authored currency or market per provision (D03 / D04). With several currencies a rate needs an identity that includes the currency; in the flat model every sibling line would have to repeat `(currency, selector)` and "all siblings agree" would be a cross-row rule with no database guard. If the Owner keeps one currency per pricing, the minimal two-level correction below is enough.

| | Minimal two-level correction | Three-level model |
|---|---|---|
| Shape | keep root + line; add `TaxIncluded` and currency-aware amount validation; keep `CurrencyId` on the root | `AncillaryPricingRate` (selector + base `Money` + application unit + tax inclusion) with `AncillaryPriceComponent` children (Tax / Fee `Money`) |
| Several currencies | no | yes, one rate per `(POS?, currency, PTC?, age?)` |
| Rate identity for a later quote | no | yes |
| Migration surface | 1–2 added columns, no row movement | 2 new tables, 69 rates + 28 components on dev, old tables kept read-only |
| Tests to rewrite | few | the pricing shape tests of Phase 1 |
| Risk | low | medium: read model, DTO and Backoffice contract change |

Field map for the three-level model (current → target):

| Current | Target |
|---|---|
| base line `Id` | `Rate.Id` (possible: each of the 69 pricings has exactly one base line per selector) |
| base line `Amount` + root `CurrencyId` | `Rate.BasePrice (Amount, CurrencyId)` |
| base line `PassengerTypeCode`, `AgeFromInclusive`, `AgeToExclusive` | same on `Rate` |
| root `FeeApplicationUnit` | **`Rate.ApplicationUnit`** — not a Fee component (see D06 below) |
| tax / fee line `Id`, `Category`, `Code`, `Name`, `CountryId`, `StationAirportId`, `Amount` | `Component` with `Value (Amount, CurrencyId of the rate)` |
| — | `Rate.TaxInclusion`: unknown for every migrated row until the Owner states it |
| root `CurrencyId`, `FeeApplicationUnit` | kept, read-only, until a separately approved cleanup |

Additive migration strategy: create the two tables and backfill by `INSERT … SELECT` (no arithmetic, no rounding); keep `AncillaryPricingLines` untouched; reconcile counts (69 → 69 rates, 28 → 28 components, 0 fee) and per-rate sums against the old grouped sums; run on an empty database and on a restored copy of dev; destructive steps only after a separate approval. Backwards compatibility: the Backoffice request and response shapes change, so the Backoffice client must move in the same release; the flat `priceLines` can be kept in the read DTO for one release, derived from the new tables.

Corrections to the proposal that this audit supports with evidence:

1. `FeeApplicationUnit` belongs to the rate's base price (section 10, D06).
2. Currency minor units need a trustworthy source before any validation is switched on (section 10, D07).
3. A per-component `IsIncludedInBase` is finer than the verified benchmark (one flag per provision). One flag on the rate is the smaller, benchmark-aligned choice; the per-component flag is a local extension the Owner may still prefer.

Real acceptance scenarios to demand before any corrective merge, beyond PR-01…14: the 69 / 97 dev rows migrate with identical ids and sums; an IRR price that is not a multiple of the currency's rounding factor (1000 on dev) — accept or refuse, by decision; a domestic IRR and an international USD rate of one service in one pricing, with the eight existing two-provision definitions left untouched; a draft edited twice in parallel; a published rate that cannot be edited.
