## 3. The endpoint

```
POST /Backoffice/v1/AncillaryOffers        (also with a trailing slash)
Authorization: Bearer <Backoffice token>   policy SurfaceAuthorization.Backoffice

{ "offerId": "<priced-offer-id>",
  "options": { "customerId": "…", "countryId": 0, "pointOfSaleId": 0, "salesDate": "…", "preferredCurrencyId": 0 } }
```

`options` and each of its members are optional. The body is the Backoffice model of AirAvail (`BackofficeFlightAvailabilityPriceRequest` = `OfferId` + `BackofficeSearchOptionsRequest`), member for member and type for type, by the Owner's ruling of 2026-10-11 ("do exactly the model AirAvail implemented at the input of its FlightOffers endpoints; each surface has its own model"). This replaces pack 02 section 1 ("exactly one input") and the pack stop condition about a point of sale in the request.

Sales scope of the Backoffice surface (the AirAvail Backoffice rule):

| Fact | Source |
|---|---|
| caller | must be an airline context with an airline user id and an airline office id, else 403 (16809) |
| owner airline | home airline of the operator (`IOperatorAirlineResolver`), never from the request or the offer |
| channel | `BackOffice` |
| point of sale | `options.pointOfSaleId` when given (not validated - AirAvail does not validate it either); otherwise the allowed set from `IPointOfSaleEligibilityReference` (channel, `options.countryId`, the caller's office) and only when that set has exactly one id; any other outcome is 409 `POS_CONTEXT_UNRESOLVED` (16808) |
| customer | `options.customerId` when it is a number (as AirAvail: anything else is ignored); customer type stays unknown |
| evaluation time | `options.salesDate`, else the clock, in UTC |
| currency | `options.preferredCurrencyId`, else the currency of the flight offer; ancillary rates are never converted |

Upstream call (same as Ordering's `OfferProvider`): `POST {Offer:BaseUrl}v1/FlightOffers/Details` with `{ "OfferId": "…" }`, no authorization header, `PropertyNameCaseInsensitive`, numbers readable from strings, enums readable from names or numbers; timeout from `Offer:RequestTimeout` (seconds) when configured. The legacy `AncillaryOffers` routes of AirAvail are never called.

Response: the framework envelope `{ "data": … }` around `AncillaryOffersDto` - `offerId`, `evaluatedAtUtc`, `currency`, `flightOffer` (flight amounts with their own currency), `scope`, `journey`, `travellers` (included baggage and fare per flight), `categories` (by the nine profiles, offers only), `offers`, `blockedOffers`, `diagnostics`, `completeness`. Enums are `{ value, name, title }` as on every Backoffice read. Each candidate carries identity, service, coverage, eligibility, selection contract, quantity, pricing lines, availability, confirmation, document, the engine's `offerReadiness`, one `displayState` and `canPurchase: false`.

- `offers` = readiness `Selectable`, `NeedsSelection`, `NeedsQuote`; `blockedOffers` = `NeedsVerification` (and `Unavailable` / `NotEligible` if the engine returns them). Display state is one switch over the readiness (`AncillaryOfferMapper.DisplayStateOf`).
- `candidateIdentity` is only the address of the candidate for a later re-evaluation. No offer id, token, hold or guarantee is created; `isGuaranteed` is false everywhere.

| Condition | Answer |
|---|---|
| no or invalid token, wrong surface | 401 / 403 from the Backoffice policy; the provider is not called |
| caller is not an airline user of an office, or no home airline | 403, code 16809 |
| point of sale unresolved | 409, code 16808, title starts with `POS_CONTEXT_UNRESOLVED` |
| empty offer id | 422, code 16803 |
| producer refuses the id (unpriced, corrupt; HTTP 400 / 404 / 422) | 422, code 16804 with the producer's reason |
| producer answers without a journey | 404, code 16805 |
| producer unreachable, timeout, 401, 5xx, unreadable or empty answer, address not configured | 502, code 16806 |
| producer answer with broken joins or another offer id | 502, code 16807 |
| no published product for owner and point of sale | 200, empty lists, diagnostic `NO_APPLICABLE_PRODUCT` |

## 5. Mapping, field by field

| Producer field | Goes to | Rule |
|---|---|---|
| `offerId` | `SourceIdentity.TrustedSourceReference`, response `offerId` | must equal the requested text, else inconsistent |
| `pricedAt` | response `flightOffer.sourcePricedAt` only | it is the sales date encoded in the id, not the time of a quote |
| `lastTicketingDate` | response `flightOffer.lastTicketingDate` only | never `ValidUntilUtc` |
| `currencyId`, `currencyCode`, base / charge / total amount | `CurrencyId` of the context (unless a preferred currency is given); response `flightOffer` with its currency | flight money is never added to an ancillary price |
| `airTransports[].boundId`, `sequence`, origin, destination | `ShoppingPortion` | unique bound ids and sequences required |
| `airTransports[].boundOfferId` | join key only | blank, duplicate, or a pricing unit covering an unknown one = inconsistent |
| `direction` (1 / 2) | response direction | other values = null |
| `flights[]` | `ShoppingFlight`; `FlightRef` = `{boundId}:F{sequence}` | flight id > 0, departure < arrival, airlines > 0; via airports of a flight = stops between its legs; via of a portion = connection airports |
| `flightCapacityId` | not read | it is neither flight identity nor ancillary stock |
| `legs[]` | response legs, flight via airports | never a sold unit |
| terminals, aircraft, cabin, RBD | `ShoppingFlight` | 0 or absent = null |
| `tickets[]` | `ShoppingTraveller` (`TravellerRef`, PTC) | PTC must be a name of `PassengerTypeCode`; no birth date, age, identity or exit-row fact is set |
| `coupons[]` | one fare fact and one baggage fact per traveller and flight | every sold flight must have exactly one coupon per ticket |
| coupon pricing lines with category Fare | `AirFareId` | exactly one numeric reference that is a fare component of the same bound; otherwise no fare fact and `FareFactsComplete = false` |
| fare component `fareBasis`, `fareType`, `bookingClass`, `cabinClassId`, `rbdId` | `TravellerFareFacts` | unknown fare type name = null |
| `fareFamily` (text) | `FareFamilyCodeOrName` | `FareFamilyId` stays null |
| baggage pieces, weight, unit (checked and cabin) | `TravellerFlightBaggageFacts`, evidence Verified | only with unit `Kg` or `Lbs`; `""` or `"0"` = unknown; a stated 0 is kept; pieces and weight are passed as sent |
| - | `OriginCountryId`, `DestinationCountryId` | from the airport reference of this service; missing row = null |
| - | `OriginIanaTimeZoneId` | null (no source) |
| - | completeness | travellers and itinerary true; fare and baggage as found; fare benefits and existing services false |
| `orderCharges`, `ratesOfExchange`, coupon amounts | not read | not needed for ancillary evaluation |

## 10. Owner decisions and next action

Decided in this task: the request model = the AirAvail Backoffice model (section 3).

Open, each with what the code does now:

1. **Point of sale without a named id.** Needs a service-to-service source of the AirPrice point-of-sale conditions (or of the allowed set for a sale). Until then: 409. When it exists and returns several ids: the engine evaluates one point of sale per call - should the endpoint then evaluate the provisions of all allowed ids in one sequence order (as AirAvail does for fares)? That is an engine change and was not made.
2. **What a provision's point of sale is.** The catalog of the development database uses the airline office id `9200000000000001`; AirPrice points of sale are other ids (staging: 1, 1470355450238074880, 1525580011535335424). Authoring validates neither. Which id space is the rule?
3. **Airport time zone.** Without it most realistic provisions stay blocked. Source to use (AirInfo airport / city zone into the reference module - a schema change there)?
4. **Offer priced on another channel.** Should the Backoffice endpoint refuse an offer id whose price call was made by another channel or customer? The producer answer cannot tell; only decoding the id could, and the pack forbids a local codec.
5. **Existing services in a pre-order flow** are reported as "not complete", so excess-piece tiers and exclusive meal families are blocked. Is "no order yet = no existing service" acceptable evidence here?
6. **Customer type** from the customer reference - wanted on this surface?
7. Commit of this work (nothing is committed).

Proposed next action: rule on 1-3 (they decide how much of a real catalog becomes sellable through this endpoint), then the same query for the next surface with its own AirAvail model.
