# P3.2C-03 - Typed definition contracts of the other eight profiles (24 variants in total)

Step 3 of `02-CODING-AGENT-PROMPT.md`, built on the Seat contract of `reports/P3.2C-02-SEAT-CONTRACT.md` with the same rule and the same code path. Baseline `feat/ancillary-v12.2-phase1-phase2-rebuild@f89a0275455717313681f5ecffb7f7b2c5f07817`; **uncommitted**.

## 1. What changed

| | BEFORE (f89a027) | AFTER |
|---|---|---|
| `GET /Backoffice/v1/AncillaryServiceDefinitions/{Profile}/{serviceDefinitionId}` | did not exist | **added for all nine profiles** (Seat in step 2, eight here). Same answer shape: state header + `form` = the `PUT` body; `form.specification` holds only the fields of the variant |
| `POST` / `PUT .../Baggage`, `Meal`, `Pet`, `AssistedTravel`, `AirportService` | every member of the profile, the kind member mandatory | same routes and use cases; the members the variant fixes may be omitted; the v1 body is still accepted and validated by the same domain rule |
| `POST` / `PUT .../Upgrade`, `Priority`, `Connectivity` | one variant each, no fixed member | **body unchanged** (nothing to omit); only summary, description and response schema were added |
| Generic `GET .../{serviceDefinitionId}`, `Paginated`, `Variants`, lifecycle routes | - | unchanged |
| Domain, Application, Persistence, Shopping, migrations | - | **not touched**; every create and change still goes through `BackofficeDefineAncillaryServiceDefinitionCommand` / `BackofficeChangeAncillaryServiceDefinitionCommand` |

Route delta of steps 2 + 3: 125 -> 134 (nine added, none changed, none removed). One shared read service (`GetAncillaryServiceDefinitionFormService`), one mapper per profile, one thin query + handler per profile; no copy of the service per profile.

The rule, unchanged from Seat: **the variant view is the v1 specification minus the members that the variant fixes or forbids.** A fixed member is filled by the presentation when the body omits it; if the body sends it, the domain rule decides as before.

## 7. Notes and open points

1. Assisted travel keeps one level of nesting (`specification.wheelchair`, `.bassinet` ...). Flattening it would make the variant body different from the v1 body, and the compatible write could then not accept both.
2. Observation, not changed: a pet animal sent with `otherCode: null` is stored and read back as `otherCode: ""` (domain normalisation; the generic read shows the same). The round trip is stable.
3. `Upgrade`, `Priority` and `Connectivity` still bind the application input types directly on write; their read uses its own DTO with the same members.
4. Still open from step 2: error responses and the two shapes of a `400` body (step 5), schema names of generic types (step 5), examples not embedded in the OpenAPI document.
