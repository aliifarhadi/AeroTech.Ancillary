## 3. What was built

### 3.1 A - server-side filtered catalog list

`GET Backoffice/v1/AncillaryServiceDefinitions/Paginated` accepts two more optional query members, `Profile` (enum name) and `VariantCode` (`A01`..`A24`). Route, grid columns, sort order (reference, newest version, id) and the eight earlier filters are unchanged.

- The two predicates are part of the same EF `Where` that feeds `LongCountAsync` and the `Skip` / `Take` page, so SQL filters before it counts and pages. The acceptance test asserts exactly two SQL commands per call, the filtered total on every page and the exact ids of every page.
- `VariantCode` is checked against `AncillaryVariant.Find` (the canonical registry, no second list): an unknown code, or a code whose registry profile differs from `Profile`, is refused with `422 / 16202` (`ServiceDefinitionIsInvalid("VariantCode")`, the code the domain already uses for the same mistake at Define). An unknown `Profile` name is a `400` from model binding.
- `totalCount` and `id` are JSON strings (platform convention for `long`); `version` of a list row is a number.

### 3.2 B - read-only canonical variant discovery

`GET Backoffice/v1/AncillaryServiceDefinitions/Variants[?Profile=<name>]` returns the entries of `AncillaryVariant.All` ordered by code. It is a literal segment, so it does not collide with `{serviceDefinitionId:long}`. No aggregate, table or second matrix was added; the DTO is projected from the registry with the existing `EnumValueDto` convention.

### 3.3 C - one real reference: flights from FlightFlow

The Owner gave the FlightFlow service address during the run; it is the `FlightFlow:BaseUrl` of the local `appsettings.Development.json` (a git-ignored file, so it is not part of the diff). FlightFlow answers `GET service/v1/Flights/{flightId}` anonymously with the flight and its operating airline, and `404` for an unknown id (probed on staging, flight `1550116065952923736`). That is an authoritative read-only source for exactly one port, `IFlightOccurrenceReference`, so the smallest production implementation was added in this repository:

- `Providers/FlightFlow/Services/FlightFlowFlightOccurrenceReference.cs` (+ three wire types), registered with `AddHttpClient` on `FlightFlow:BaseUrl`, the registration shape of `ReferenceData` in this repository and of Ordering. The stub `NotConnectedFlightOccurrenceReference` was removed.
- Fail-closed mapping: `200` with the same flight id and `operatingAirlineId` = owner -> `Verified`; `404`, or a flight operated by another airline -> `NotFound` (`422 / 16609`); any other status, an unreadable or mismatching body, a transport failure, a timeout or a missing base address -> `SourceUnavailable` (`409 / 16608`). Nothing is cached or copied.
- It does not make any configuration activatable on its own: a flight-count or flight-weight source also needs its resource reference (section 4).

### 4.3 The exact missing contracts

1. **Inventory resource** - a read-only lookup `(ownerAirlineId, kind: FlightCount | FlightWeight, resourceId) -> exists and is active`. No service defines such a resource today; the Owner must name its owner first (FlightFlow, AirInfo, or an Ancillary-owned reference - the last one is a new aggregate and was not allowed here).
2. **Airport facility** - a read-only lookup `(ownerAirlineId, facilityId) -> airportId, IANA time zone, active`. AirInfo is the natural owner (it has `Locations/Airports` and `Locations/AirportTerminals`), but it has no facility entity.
3. **Counting family** - a registry of the family codes a passenger usage limit may count in, per airline. No owner exists.
4. **FlightFlow delegation** - a read-only FlightFlow statement that it is the inventory authority for a provider key of an airline (for example a capability read next to `Service/v1/Flights`). The existing `Seat-Holds` commands are Phase 3 operations and prove nothing at configuration time.

Until they exist the four ports stay `NotConnected` and activation stays refused. No local shadow table, no accepted-by-default answer and no inferred id was added.

## 8. Decisions taken in this run and observations

1. **Flight ownership rule (mine, taken without asking first - needs a ruling).** A flight is `Verified` only when its `operatingAirlineId` equals the owner airline; a flight the owner only markets is `NotFound`. Basis: physical count and weight capacity belongs to the operating carrier (my recollection of codeshare practice, **not benchmarked** against IATA or a vendor text). It is the narrower, fail-closed choice; the alternative is operating or marketing.
2. **Boundary pins were widened** for the one FlightFlow reference (section 7). The earlier pin "no HttpClient outside ReferenceData" was a pack rule; this prompt asks for a production reference where a real source exists.
3. **No timeout or retry is configured** on the FlightFlow client (same as the existing registrations here and in Ordering); `FlightFlow:RequestTimeout` / `RetryCount` in the settings file are not read by anything. A stalled FlightFlow would hold an Activate request up to the framework default.
4. **A missing `FlightFlow:BaseUrl` is tolerated, not fail-fast.** The registration copies the existing `AirInfo` / `AeroCore` registrations of this repository (base address set only when the setting exists); a host without it starts and keeps flights `SourceUnavailable`. The tracked `appsettings.json` has no `FlightFlow` section; only the local, git-ignored `appsettings.Development.json` has it. If the Owner wants start-up failure instead, it is a two-line change.
5. **Flight status is not examined.** FlightFlow `FlightStatus` has 13 values (Scheduled 1, Open 2, Closed 3, Canceled 4 ... Completed 12, Pending Review 13); the reference reads only id and operating airline, so a Canceled or Completed flight that FlightFlow returns is `Verified`. Which statuses may carry a new inventory source is a product rule nobody has stated.
6. **One SQL timeout was observed** in an earlier attempt of the HTTP run (not in the recorded run): `POST .../Pet` answered 500 after 30 s. The host log shows the 30 s command timeout on the first split query of `AncillaryServiceDefinitionRepository.ListVersionsAsync` (14 one-to-one joins with a sort). When the same request was repeated, a sample of `sys.dm_exec_requests` six seconds in showed that query suspended on `RESOURCE_SEMAPHORE` (waiting for a memory grant); two minutes later SQL Express held 237 MB at 59 % memory utilisation, and three further repeats took 0.12 s each. So the cause is inferred from the repeat, not measured on the failing request itself. Not changed here (a query or schema change is outside this prompt); it deserves a decision before load.
7. An unknown `Profile` number in the list or variant query is not an error: it matches nothing (same as the existing `Status` filter). An unknown `Profile` name is a 400.
8. **`Variants` returns a plain array, not `GridData`.** It is the only Backoffice query in this repository (and in Ordering) that returns a list without pagination. I read the prompt ("returns all 24 entries") as an options source for a select box, not a grid; the standing platform rule says Backoffice lists are paginated grids. I did not ask before building it - needs a ruling (changing it is a small edit).
9. **The FlightFlow reference writes no log** when it answers `SourceUnavailable` (status, timeout or unreadable body are not distinguishable afterwards). No HTTP client in this repository or in Ordering logs either, so none was added; for operations this is a gap.
10. **Note for the UI:** every grid column is announced as `isSortable: true` and the OpenAPI lists `SortBy` / `SortDirection`, but no list service in this repository (or in Ordering) applies them - the order is fixed (definitions: reference, newest version, id). Existing platform behaviour, not changed.
