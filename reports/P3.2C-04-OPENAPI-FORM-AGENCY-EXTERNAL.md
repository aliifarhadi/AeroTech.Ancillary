## 2. Priority 1 - the OpenAPI defect and its correction

### What was wrong in commit `396d134`

Found by validating the 24 example files against the published document with an OpenAPI-aware validator (NJsonSchema through NSwag, test `P32C_OAS_01`):

```text
Total tests: 35
Passed: 13
Failed: 22
P32C_OAS_01: "#/specification NotOneOf"
P32C_OAS_03: expected 18 choices decided by variantCode, found the choices on `specification` instead
```

1. `specification` was published as `oneOf` of the variant schemas, but the alternatives were not exclusive: Standard seat and Preferred seat have the same members, so have Lounge and Fast track, and the all-optional baggage shapes accept each other's bodies. `oneOf` requires exactly one match, so 21 of the 24 examples were invalid against their own schema.
2. Every variant schema carried `allOf` to an empty base schema with `additionalProperties: false`.
3. Nullable members that reference a schema (enums and objects) were not marked nullable, for example `allowanceConcept: null`.

### What is published now

- The choice is made where it can be decided: on the body. `POST` / `PUT` request bodies and the `form` of the read are a `oneOf` over one schema per variant, each with `variantCode` restricted to its own code and `specification` typed as that variant's schema, plus a `discriminator` on `variantCode` with a full mapping. 18 such choices exist (6 profiles with more than one variant x define, change, form). The three single-variant profiles only get `variantCode` restricted to their code.
- No empty base and no superset schema is published any more.
- Nullable references are written as `allOf` + `nullable: true`.

Example (`DefinePreferredSeatDefinition`, shortened to the two members that carry the choice):

```json
{
  "SeatSpecificationRequestDefineServiceDefinitionRequest": {
    "oneOf": [
      {
        "$ref": "#/components/schemas/DefineStandardSeatDefinition"
      },
      {
        "$ref": "#/components/schemas/DefinePreferredSeatDefinition"
      },
      {
        "$ref": "#/components/schemas/DefineExtraSeatDefinition"
      }
    ],
    "discriminator": {
      "propertyName": "variantCode",
      "mapping": {
        "A07": "#/components/schemas/DefineStandardSeatDefinition",
        "A08": "#/components/schemas/DefinePreferredSeatDefinition",
        "A09": "#/components/schemas/DefineExtraSeatDefinition"
      }
    }
  },
  "DefinePreferredSeatDefinition": {
    "description": "A08 Preferred seat",
    "properties": {
      "variantCode": {
        "enum": [
          "A08"
        ],
        "type": "string"
      },
      "specification": {
        "$ref": "#/components/schemas/PreferredSeatSpecificationDto"
      },
      "...": "the other members of the body"
    },
    "additionalProperties": false
  },
  "OverweightBagSpecificationDto.allowanceConcept": {
    "allOf": [
      {
        "$ref": "#/components/schemas/BaggageAllowanceConcept"
      }
    ],
    "nullable": true
  }
}
```

Runtime is unchanged: the v1 body with the fixed members is still accepted and validated by the domain rule; the schemas describe the variant shape, and the description of the choice names the v1 members.

## 4. Priority 3 - agency API answer (Api surface only)

The OtaPanel and Backoffice DTOs, mappers and golden files are untouched (`git status` shows only the three `api-*.json` golden files changed).

### Benchmark and decisions

| Topic | Amadeus Flight Offers Price 1.3.0 (official specification) | This API now | Note |
|---|---|---|---|
| Place of ancillaries | `included.bags`, `included["other-services"]`: maps keyed by an id | the same two maps, keyed by the offer item reference | seats are under `other-services` (Amadeus prices seats inside a seat map, which has no source here) |
| Bag entry | `quantity`, `weight`, `weightUnit`, `name`, `price { amount, currencyCode }`, `bookableByItinerary`, `segmentIds`, `travelerIds` | the same members | `quantity` 1 per piece product, empty for a weight package; `weight` from the catalog definition, in `KG` |
| Other service entry | `name`, `price`, `bookableByTraveler`, `bookableByItinerary`, `segmentIds`, `travelerIds` | the same members | `name` is the variant name in upper snake case (Amadeus lists only two values) |
| Amounts | strings | strings, at least two decimals, never rounded | AirAvail's agency answer uses two decimals |
| Traveller and segment ids | ids of the flight offer | `"1"`, `"2"`, ... exactly as AirAvail's agency flight offer numbers them | verified in AirAvail source: traveller id = position in `PassengerPricings` (the producer's `TravellerIndex`); segment id = running number per **leg** over bounds, flights, legs (`OtaFlightOffersMapper.cs:89`) |
| Places, carriers, currency | IATA codes, currency codes | `iataCode`, `carrierCode`, `currencyCode` from the reference data; no platform numeric id | a code the reference data does not hold is left empty, never guessed |
| What Amadeus has no member for | - | one extension object `ancillary` per entry: `type` (`CHECKED_BAGS`, `MEALS`, `SEATS`, `OTHER_SERVICES`), `service` (catalog identity, RFIC / RFISC, SSR), `pricing` (base, total, taxes, fees, order-level fees, completeness), `quantity`, `selectionRequirements`, `availability`, `confirmationRequirement`, `readiness`, `canPurchase`, `reasons` | everything the engine decided is still shown; nothing is recalculated in the mapper |
| Envelope | `data`, `included`, `dictionaries`, `warnings` | `meta { count, withheldCount, status }`, `data { type, flightOfferId, travelers, segments }`, `included` | `dictionaries` and `warnings` are not published (codes are inline) |

`Details` and `Selections/Evaluate` answer with `data { type, ... }` and embed the same `bag` / `otherService` entry; rates and the selected price use `currencyCode` and string amounts; the included allowance refers to `travelerId` and `segmentIds`.

### Open points of the agency API (not solved in this round)

1. **Live proof is impossible today**: every agency operation stops at the point-of-sale reference (409 / 16808), so no real agency answer in the new shape exists. The shape is proven by tests and golden files only.
2. The reader of the reference codes (`ApiOfferReferencesReader`: three key lookups on airports, airlines, currencies and the active baggage definitions) has no automated test of its own and is not reached by the live flow for the same reason; its wiring is exercised (the handler is built before the 409).
3. Segment order: AirAvail's agency answer walks `SelectedBoundOffers`, the producer of the details walks `BoundOfferSets`. That the two orders can never differ cannot be proven from this repository (joint check with AirAvail).
4. Request side: `Selections/Evaluate` still takes `infantRef`, `guardianRef`, `childRef` in the internal traveller form, which the answer no longer shows. An agency cannot express an A18 / A19 selection until the input accepts traveller ids. `selectionRequirements` still names the engine fields (`TravellerRef`, `BoundRef`, `FlightRef`).
5. `specification` in the Api detail is still the nine-branch object.
6. The list reads the active definitions of the owner once more to state the bag weight (the engine result does not carry the specification).
